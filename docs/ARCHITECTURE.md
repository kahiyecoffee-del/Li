# Dayly — Architecture

## 1. Overview

```

                                      └──────────────────────────────────────────────────────────┘
```

**Principles**
- *Local-first*: every screen reads/writes the on-device database; the cloud is replication.
- *Deterministic numbers*: Life Score, budget, goals, streaks, badges, insights and reports are pure Dart engines (`lib/domain/engines`). AI only phrases, plans and proposes.
- *AI behind a backend*: no API keys in the app. Every AI call is authenticated, App Check–protected, rate-limited, credit-metered and validated twice (server + client).
- *Every AI action needs confirmation*: proposals are rendered as cards; nothing runs until the user taps **Confirm**. Money is never moved.
- *Graceful degradation*: without `google-services.json` the app runs in **on-device mode** (local auth, no sync/AI/purchases) so it is always runnable.

## 3. Database

### On device (source of truth)
One sembast database per signed-in uid (`lifeos_<uid>.db`). Each record is a JSON map with sync
metadata `id`, `updatedAt` (epoch ms, strictly increasing per record), `deleted` (tombstone).
An `_outbox` store lists records awaiting upload.

### Firestore schema
| Path | Writer | Contents |
|---|---|---|
| `users/{uid}/profile/profile` | client | name, focusAreas, currency, income/fixed/savings (minor units), routine, food prefs, place, news topics |
| `users/{uid}/tasks/{id}` | client | title, priority, estimatedMinutes, category, deadline, scheduledAt, recurrence, completedAt |
| `users/{uid}/transactions/{id}` | client | type (expense/income), amountMinor, currency, category, date, description, merchant, source |
| `users/{uid}/budgets/{period_start_cat}` | client | weekly/monthly limits (optional category) |
| `users/{uid}/habits/{id}`, `habit_logs/{habitId_day}` | client | habit definition; per-day count |
| `users/{uid}/mood_logs/{day}`, `sleep_logs/{day}` | client | 1–5 mood + note; minutes slept |
| `users/{uid}/meal_plans/{day}`, `pantry_items/{id}`, `shopping_items/{id}` | client | food |
| `users/{uid}/ai_memories/{id}` | client | category, content (user-visible/deletable) |
| `users/{uid}/daily_scores/{day}`, `daily_goals/{day}`, `achievements/{badge}` | client | history for trends/reports |
| `users/{uid}/devices/{fcmToken}` | client | platform, locale, timeZone |
| `entitlements/{uid}` | server | premium, productId, expiresAt, autoRenewing, state |
| `usage/{uid}`, `usage/{uid}/days/{day}` | server | credits used, bonus, rewarded ads, tokens, `estimated_ai_cost_per_user` |
| `rate_limits/{uid}`, `purchases/{tokenHash}`, `ssv_transactions/{tx}`, `billing_events/*` | server | abuse prevention & billing audit |
| `ai_cache/{hash}`, `news_cache/{provider_lang_topic}` | server | response caches (TTL on `expiresAt`) |
| `metrics_daily/{day}` | server | AI cost per active user, rewarded ads per user, premium actives |

**Never synced** (privacy): `journal_entries` (AES-256-GCM encrypted on device, key in Android Keystore)
and `ai_conversations` (only the recent window + rolling summary is sent per request).

Spec mapping: the spec's `expenses` → `transactions` (expenses + extra income), `recipes` are embedded in
`meal_plans` and the bundled recipe library, `shopping_lists` → `shopping_items`, `notifications` →
on-device planner (no per-notification documents), `subscriptions` → `entitlements` + `purchases`,
`analytics` → Firebase Analytics + `metrics_daily`.

Rules (`firebase/firestore.rules`) only allow owners to access their own subtree, only for allow-listed
collections, require valid sync metadata and `_serverTs == request.time`, forbid hard deletes, and keep
entitlements/usage/caches server-only. Tested against the emulator in `firebase/rules-test`.

## 4. Offline-first sync & conflict resolution
- **Writes**: `Repository.save()` writes locally and enqueues `{collection,id}` in the outbox atomically.
- **Push**: `SyncEngine` uploads outbox records (`set` with `_serverTs: serverTimestamp()`), then acks only
  if the record wasn't modified meanwhile.
- **Pull**: per collection, pages through `_serverTs > cursor` ordered by (`_serverTs`, doc id). Server
  timestamps make cursors immune to device clock skew.
- **Conflicts**: last-write-wins per record by client `updatedAt` (user intent time). Ties prefer the
  tombstone, then the server copy. A remote record older than a local edit re-queues the local edit.
- **Trade-off**: concurrent edits to *different fields* of the same record are not merged; records are
  small and mostly per-day keyed (`habit_logs/{habit_day}`, `mood_logs/{day}`), which keeps this rare.
- **Triggers**: debounced after local writes, on reconnect, on app resume, pull-to-refresh.
- Tombstones are purged locally after 30 days once uploaded.

## 5. Deterministic engines
- **Budget** (`budget_engine.dart`): integer minor units. Discretionary pool = income + extra income −
  savings goal − max(planned fixed, fixed spent). Safe daily = (pool − variable spend before today) / days
  left incl. today, capped by an active weekly limit. Fixed categories: housing, bills, subscriptions.
- **Life Score** (`life_score_engine.dart`): weighted average of available components — money 20,
  productivity 20, health 15, habits 15, mood 10, sleep 10, planning 10. Missing data is excluded (weights
  renormalised). `explain()` diffs against yesterday's stored snapshot and names the top two factors.
- **Daily goals**: 3–5 goals from budget, top task, scheduled habits (health first if Health is a focus),
  mood/sleep check-ins, plan-your-day. "Life Progress" = % completed.
- **Streaks / badges / insights / reports**: pure functions with thresholds documented inline.

## 6. AI architecture
Client: `AiService` (Cloud Functions client) → `AiResponseParser` → `AiActionValidator` → confirmation
card → `AiActionExecutor`. `MemoryManager` (user-visible memories, free-tier limit), `AiContextBuilder`
(only consented scopes: money, tasks, habits, mood, food, journal — journal off by default).

Server (`functions/src/ai`):
| Component | File |
|---|---|
| AIProvider abstraction (Anthropic SDK, OpenAI, Gemini) | `types.ts`, `providers/*`, `registry.ts` |
| PromptManager (versioned, stable prefix for caching) | `prompts.ts` |
| Structured output schemas | `schemas.ts` |
| AIResponseValidator / action parser | `validator.ts` |
| Model routing, credit cost, output budgets | `router.ts` |
| Cost estimation (`estimated_ai_cost_per_user`) | `cost.ts`, `usage/credits.ts` |
| Response cache (tasks) | `cache.ts` |
| Conversation compression | `handlers.ts` (`toSummarize` → rolling summary via fast model) |

Cost controls: cheap model for simple chat and all tasks; capable model only for complex/premium
requests; output token caps; provider prompt caching (stable system prompt); 24h task cache; history
window of 8 turns + summary; per-user daily credits, rate limit (8/min) and premium fair-use cap.

## 6b. On-device AI
Two layers run without any server:

1. **Text classifiers** (`assets/models/*_classifier.json`, ~50 KB each) — multinomial logistic
   regression over hashed word + character 3/4-grams, int8 weights, pure-Dart inference
   (`lib/domain/ml/text_classifier.dart`). Used for expense categories (smart input, receipt merchant)
   and shopping aisles, **after** the keyword dictionary and only when the probability is ≥ 0.7;
   otherwise the cloud AI or the user decides. Trained by `tool/ml/train_classifiers.py` (pure Python,
   seeded, synthetic en/tr data from `tool/ml/vocab.py`); `test/unit/text_classifier_test.dart` checks
   Dart/Python parity to 1e-9. Measured on held-out data (see `metrics` in each model file):

   | | expense | shopping |
   |---|---|---|
   | fresh typos of known terms (model) | 77% | 81% |
   | same typos, previous keyword matcher | 8% | 3% |
   | never-seen terms, precision when confident (≥0.7) | 87% | 90% |
   | never-seen terms, share answered confidently | 18% | 23% |

   i.e. the model fixes typos/variants well and abstains on words it cannot know.

2. **Offline assistant** (`lib/services/ai/offline/`) — an optional, downloadable small LLM (MediaPipe
   `.task`, e.g. Gemma 3 1B int4 ≈ 550 MB) run with `flutter_edge_ai` + `flutter_edge_ai_mediapipe`.
   Used when the model is installed and the device is offline, the backend is unavailable, or the user
   prefers it; also as automatic fallback when a cloud call fails with a network error. Replies are
   **text only** (no actions — small models are not reliable at structured output), use a trimmed copy
   of the consented context, consume no credits, and are labelled "Offline answer". Download URL and
   size come from Remote Config (`offline_model_url`, `offline_model_size_mb`); gated by the
   `offline_ai` premium feature by default.

## 7. Monetization
- **Rewarded ads** (primary): user-initiated only — extra AI credits, today's detailed score, monthly
  report preview. AI-credit rewards are granted **by the server** (callable, capped per day) or via AdMob
  **SSV** (`REWARD_MODE=ssv`, signature-verified, idempotent).
- **Interstitials**: off by default (`interstitial_frequency=0`); when enabled, only at natural breaks
  (closing a report), never for Premium, never in the first 3 days, capped per day (`AdPolicy`).
- **Banners**: only on browsing screens (Life hub, reports) when `banner_enabled`.
- Never during forms, money entry, AI conversations or onboarding (enforced by `AdMoment`).
- **Premium**: Google Play subscriptions; verified server-side (Play Developer API), token bound to one
  account, entitlement written by the server, RTDN keeps it current. Gating via `premium_features`.
- UMP consent (GDPR) is collected before any ad request.

## 8. Remote control, feature flags & A/B tests
All limits, ad frequency, notification caps, premium feature list and feature flags live in Remote
Config (`firebase/remoteconfig.template.json`); the server reads the same keys via the server template.
`Experiments` reads variants assigned by **Firebase A/B Testing** (`experiments` JSON param) and logs an
`experiment_exposure` event; there is no client-side randomisation. Wired experiments: onboarding
(short variant), home layout (compact), rewarded placement (inline), paywall (annual first),
notifications (reserved).

## 9. Notifications
`NotificationPlanner` (pure) decides the next ~36h: task reminders 30 min before, plus nudges (streak
at risk, log spending, budget tight, mood check-in, Sunday weekly review) capped per day by Remote
Config, skipped when already satisfied, never in quiet hours (bedtime→wake time). Frequency: off /
reminders only / normal. Re-planned on data changes and app resume. FCM tokens are registered for
server-sent pushes (infrastructure only; no server campaigns are implemented).

## 10. Security & privacy
API keys only in Secret Manager; App Check (Play Integrity) enforced on callables; Firestore rules;
rate limiting and credits; purchase token binding; SSV signature verification; AI output validated on
both sides and never executed; journal encrypted & local; `allowBackup=false`; analytics/crash/ads
personalisation opt-outs; data export (JSON) and full account deletion (server + device).

## 11. Analytics
Events: see `AnalyticsEvent` in `lib/services/analytics/analytics_service.dart` (all spec events plus
`task_created`, `habit_completed`, `paywall_viewed`, `experiment_exposure`, `retention_day`, …).
Retention: Firebase computes D1/D3/D7/D14/D30 cohorts from `first_open`/`app_open`; `retention_day`
(with `milestone=dN`) and the `install_week` user property support custom funnels.
